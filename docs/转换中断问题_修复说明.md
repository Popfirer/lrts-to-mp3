# 转换中断问题 · 根因与修复说明

> 针对「北宋大丈夫」「天下」两次批量转换都出现"转码了但正式文件还是假 MP3"的问题。
> 修复文件：`F:\desktop\懒人听书转换\lanren_convert.py`

---

## 一、现象

两次都出现同一个错位状态：**真 MP3 卡在 `.__tmp.mp3` 临时名下，正式 `.mp3` 仍是未转换的 MP4 容器**。

| 书目 | 卡住的 tmp | 分布特征 |
|---|---|---|
| 北宋大丈夫 | 245 个 | 两个**连续段**：117–138、1164–1386 |
| 天下 | 5 个 | 003–007，全部出现在同一 26 秒窗口内 |

界面/日志当时都显示"转换完成"，用户并不知道出了问题。

---

## 二、根因（两个缺陷叠加）

### 缺陷 1：改名归位失败，却被统计成"成功"（主因）

转码流程是「ffmpeg 先写临时名 → 再改名覆盖同名文件」：

```python
transcode_to_mp3(src, tmp, ffmpeg, tags)   # 写出 stem.__tmp.mp3
...
if os.path.abspath(tmp) != os.path.abspath(dst):
    os.replace(tmp, dst)                   # 改名归位，覆盖同名 MP4 容器
...
stat["ok"] += 1        # ← 原代码无论上面成功还是抛异常，都 +1
```

Windows 上，若目标文件此刻正被**杀软 / 天锐绿盾 DLP / 系统索引器**打开，`os.replace` 会抛
`PermissionError(ERROR_ACCESS_DENIED)`。这种占用通常只持续零点几秒，但原代码**只尝试一次就放弃**，
而且**照样计入 ok** —— 于是"转换成功"是假的，真 MP3 就永远停在临时名上。

### 缺陷 2：归位动作在主线程序列执行，一次阻塞会拖垮全局（放大器）

`os.replace` 原本在主线程的 `as_completed` 循环里执行。若某次 replace 被过滤驱动**长时间挂起**
（不是立刻报错，而是阻塞），主线程就停摆；而此时 6 个 ffmpeg 工作线程仍在从任务队列取活、
不断产出新的 `.__tmp.mp3`。

这正好解释了观测到的**连续段**分布（117–138、1164–1386）——那不是随机锁冲突的样子，
而是"收尾流水线被卡住后，上游还在持续产出"的典型特征。

> 对照：后续用旧代码跑「北宋大丈夫」883 个文件时 ok=883、零残留，说明这不是稳定必现的锁，
> 而是**偶发的瞬时占用 + 不重试 + 主线程阻塞**共同触发。

## 三、修复内容（已落地）

| # | 修复 | 说明 |
|---|---|---|
| 1 | 新增 `safe_replace()` | 只对**占用类**错误（winerror 5/19/32/33/1224、errno 11/13）退避重试 5 次（0.5→2.5s，累计约 7.5s）；其它错误立即失败，不做无谓等待 |
| 2 | 归位移入工作线程（新增 `_one()`） | 「转码 + 归位」在同一条线程内完成；单次阻塞只卡住一条 lane，不再拖垮整个收尾循环 |
| 3 | 成功判定改为**验后置条件** | 只有 `detect_audio_ext(dst) == ".mp3"`（目标确实是真 MP3）才计 `ok` |
| 4 | 新增 `swapfail` 统计 + 醒目日志 | 归位失败时**保留 tmp**（不删除），并在日志里明确报"有 N 个未归位"，不再假装成功 |
| 5 | 沿用并复用了完整性校验 | 下次运行开头会自动：完整 tmp → 归位；截断残次品 → 丢弃重转 |

关键改动（节选）：

```python
def safe_replace(tmp, dst, tries=5, delay=0.5):
    RETRYABLE = {5, 19, 32, 33, 1224}          # 拒绝访问/写保护/共享冲突/锁冲突/被映射
    for i in range(max(1, tries)):
        try:
            os.replace(tmp, dst)
            return True
        except OSError as e:
            winerr = getattr(e, "winerror", None)
            if not (winerr in RETRYABLE or getattr(e, "errno", None) in (11, 13)):
                break                           # 非占用类错误: 立即放弃
            time.sleep(delay * (i + 1))
    return False
```

```python
def _one(src, dst, tmp, tags):                  # 在工作线程里跑完"转码+归位"
    if not transcode_to_mp3(src, tmp, ffmpeg, tags):
        return "fail"
    if os.path.abspath(tmp) != os.path.abspath(dst) and not safe_replace(tmp, dst):
        return "swapfail"                       # 保留 tmp, 下次自动恢复
    if os.path.abspath(src) != os.path.abspath(dst):
        os.remove(src)
    return "ok" if detect_audio_ext(dst) == ".mp3" else "swapfail"
```

## 四、验证结果

### `safe_replace` 单元测试

| 场景 | 结果 |
|---|---|
| 正常归位 | ✅ 返回 True，dst 更新，tmp 消失 |
| dst 被独占占用 | ✅ 重试 1.2s 后返回 False，**tmp 保留**、dst 未被破坏 |
| 不可重试错误（tmp 不存在） | ✅ 0.00s 立即失败，不做无谓重试 |
| 占用在重试期间解除 | ✅ 自动成功 |

### 端到端 / 自愈测试

| 场景 | 结果 |
|---|---|
| 3 个假 MP3 全流程 | ✅ `ok=3, fail=0, swapfail=0`，全部转成真 MP3，无 tmp 残留 |
| 自愈 A：遗留**完整** tmp | ✅ 直接归位（8s 时长原样保留），不重复转码 |
| 自愈 B：遗留**截断** tmp（3s / 源 30s） | ✅ 丢弃残次品并**重新转码到完整 30s**，源文件未被覆盖 |

---

## 五、以后再遇到怎么办

1. **中断后直接重跑程序即可**——完整的 tmp 会自动归位、截断的会自动重转，**不会丢音频**。
2. 若日志出现"未归位 / swapfail"，说明文件被杀软或绿盾占用：
   把 `F:\desktop\懒人听书转换\workspace\` 加入**实时扫描排除项 / 白名单**，或换个时间重跑（tmp 还在，重跑即恢复）。
3. 关闭界面时尽量不要在"阶段 3 转码"进行中强杀进程；即使强杀也只是留下 tmp，重跑可恢复。
